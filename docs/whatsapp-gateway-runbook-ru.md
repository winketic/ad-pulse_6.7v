# WhatsApp-шлюз: операционный runbook

Короткая инструкция на случай, когда «сообщения не приходят». Написана так,
чтобы разобраться самому за 5 минут, не читая код.

---

## Что где лежит

| Что | Где |
|---|---|
| Код шлюза | VPS `162.35.31.85`, каталог `/opt/adpulse-whatsapp` |
| Сессии WhatsApp (креды) | `/opt/adpulse-whatsapp/data/auth/<company_id>/` |
| Кэш чатов | `/opt/adpulse-whatsapp/data/chats/<company_id>.json` |
| Скачанные фото и голосовые | `/opt/adpulse-whatsapp/data/media/<company_id>/` |
| Недоставленные вебхуки | `/opt/adpulse-whatsapp/data/outbox/` |
| Секреты шлюза | `/opt/adpulse-whatsapp/.env` (chmod 600) |
| Системные сервисы | `adpulse-whatsapp.service`, `caddy.service` |
| Публичный адрес | `https://162-35-31-85.sslip.io:8443` |
| Приложение | Vercel, проект `ad-pulse` |

**Главное правило:** каталог `data/` — это живые сессии. Удалили его — все клиенты
сканируют QR заново.

## Быстрая диагностика: три команды

Запускать на своём Mac из корня проекта:

```bash
npm run check:whatsapp      # живы ли шлюз, токен, вебхук, таблицы
npm run inspect:whatsapp    # состояние сессии, сколько чатов, что отмечено
```

Проверить, что шлюз не течёт по памяти:

```bash
ssh root@162.35.31.85 'systemctl show adpulse-whatsapp -p MemoryCurrent -p MemoryPeak'
```

Если `MemoryCurrent` близко к `MemoryPeak` и пик не растёт сутками — всё в порядке.
Рост пика день ото дня — повод разбираться.

Если оба зелёные — проблема в конкретном сообщении, смотрите логи:

```bash
ssh root@162.35.31.85 'journalctl -u adpulse-whatsapp -f'
```

В логах теперь есть строка на **каждое** сообщение:

```
INFO [session] сообщение chat="Снабжение" fromMe=true тип=text
INFO [session] сообщение пропущено chat=1203634032@newsletter fromMe=false
```

Если строки нет — сообщение до шлюза не дошло (проблема в WhatsApp-соединении,
а не в приложении).

## Симптом → причина → что делать

### «Пишу в группу, ничего не появляется»

1. **Строка в логе есть, `fromMe=true`** — всё нормально, сообщение принято.
   Дальше смотрите, попал ли чат в отслеживаемые: `npm run inspect:whatsapp`
   покажет список отмеченных. Если чата нет — отметьте его на
   `/dashboard/whatsapp/connect`.
2. **Строки в логе нет** — сессия отвалилась. Проверьте `npm run inspect:whatsapp`,
   статус должен быть `open`. Если `logged_out` — нужно привязать номер заново.
3. **Строка есть, но `пропущено`** — сообщение не в личном чате и не в группе
   (рассылка, статус). Игнорируется намеренно.

### «Сообщение в очереди, но транзакция не создалась»

Так и задумано. Автоматически создаётся только при уверенном разборе
(`confidence: high`). Причины ручного разбора:

- материала нет в справочнике компании — название в сообщении должно совпадать
  с карточкой материала;
- неоднозначная единица измерения;
- фото или голосовое не распозналось (`media_unreadable: true`).

Подтвердить можно на странице `/dashboard/whatsapp` в очереди.

### «Голосовые не распознаются»

Провайдер разбора (`alem.ai`, модель `gemma4`) принимает текст и картинки, но не
аудио. Голосовые уходят в очередь с пометкой. Включится, когда появится
провайдер с транскрипцией (например, OpenAI Whisper с рабочим балансом).

### «`/health` показывает `pending` больше нуля»

Это очередь недоставленных вебхуков: приложение было недоступно (деплой или
сбой) и сообщения отложены. Шлюз повторяет их раз в минуту сам. Если `pending`
растёт — приложение лежит, проверьте его отдельно.

### «Сессия `logged_out`»

WhatsApp отвязал устройство (нажали «Выйти» на телефоне, сменился пароль,
истекла сессия). Шлюз пришлёт алерт в Telegram и пересоздаст сессию при
следующей попытке подключения — клиенту нужно отсканировать QR заново.

### «QR не появляется»

```bash
ssh root@162.35.31.85 'systemctl status adpulse-whatsapp --no-pager -n 30'
```

Частые причины: нет сети до `web.whatsapp.com`, закончилось место на диске
(`df -h /`), повреждён каталог сессии. Повреждённую сессию можно удалить:
`rm -rf /opt/adpulse-whatsapp/data/auth/<company_id>`, затем подключить заново.

## Деплой изменений

**Шлюз** (с VPS или локальной машины):

```bash
rsync -az --exclude node_modules --exclude dist --exclude data --exclude .env \
  -e "ssh -i ~/.ssh/id_ed25519" whatsapp-gateway/src/ \
  root@162.35.31.85:/opt/adpulse-whatsapp/src/

ssh root@162.35.31.85 'cd /opt/adpulse-whatsapp && npx tsc && systemctl restart adpulse-whatsapp'
```

Перезапуск **не требует** повторного сканирования QR — сессия лежит на диске.

**Приложение** (Vercel):

```bash
npx vercel --prod --yes
```

Автодеплоя с GitHub нет: `git push` сам по себе прод не обновляет.

## Пределы и риски

- Сервер делит ресурсы с VPN пользователя (xray на 443, Hysteria2 на UDP 8443).
  У шлюза жёсткий потолок `MemoryMax=1400M`, чтобы утечка не уронила VPN.

**Замерено 2026-11-08** (одна живая сессия, 295 чатов, 19 минут работы):

| Показатель | Значение |
|---|---|
| RSS процесса | 121 МБ |
| Память cgroup (`MemoryCurrent`) | 70 МБ |
| Пик за всё время (`MemoryPeak`) | 70 МБ — **равен текущему, утечки нет** |
| CPU | 0.1% |
| Данные на диске (сессия + кэш чатов) | 224 КБ |

Вывод: **память не является узким местом** — на 2.6 ГБ свободных помещается
десяток номеров. Ограничивает другое: 1 vCPU (пик при первичной синхронизации
истории) и то, что рядом живёт VPN пользователя. Для нескольких клиентов всё
равно нужна отдельная машина, но из-за CPU и изоляции, а не из-за RAM.
- Baileys — неофициальный доступ к WhatsApp. Бан номера возможен, поэтому
  клиентам стоит подключать **выделенный** номер, а не основной канал снабжения.
- TLS-сертификат на `162-35-31-85.sslip.io` продлевается Caddy автоматически.
  Если сервер переедет на другой IP — адрес изменится, нужно обновить
  `WHATSAPP_GATEWAY_URL` в Vercel и `APP_URL` в `.env` шлюза.

# в базе: дошли ли сообщения от шлюза
select provider, count(*) from wazzup_messages group by 1;

# какие чаты отмечены
select chat_name, chat_jid, is_watched from whatsapp_chats where is_watched;

# создались ли движения из WhatsApp
select count(*) from material_transactions where source = 'whatsapp';
