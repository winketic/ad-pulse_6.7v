# Исследование: отказ от Wazzup / свой WhatsApp-шлюз

Дата: 2026-11-08
Вопрос: можно ли не использовать Wazzup, а сделать интеграцию самим — чтобы клиент прикрепил свой номер,
сам выбрал нужные чаты по названию (а не разбирался с chat_id), и мы чекали только эти чаты.

---

## TL;DR

1. **Блокер не в Wazzup.** Названия чатов **уже приходят в наш вебхук** и просто выбрасываются.
   Сценарий «клиент выбирает чат по названию из списка» реализуется на текущем стеке за ~1 день,
   без отказа от Wazzup и без единого нового внешнего API.
2. Полный отказ от Wazzup возможен двумя путями: официальный Cloud API Meta (нет списка чатов и почти нет групп)
   или неофициальный шлюз на Baileys (даёт всё, но нарушает ToS и требует отдельного постоянного сервера).
3. Рекомендация: сначала закрыть UX за 1 день (Вариант 0), self-hosted шлюз рассматривать позже и только
   как отдельный продукт с отдельной инфраструктурой.

---

## 1. Что реально есть в Wazzup API (проверено по докам 2026-11-08)

Источник: https://wazzup24.ru/help/api/ (детально: `/messages/`, `/groups/`, `/contacts/`, `/webhooks/`)

| Возможность | Есть? | Метод |
|---|---|---|
| Отправка сообщений | да | `POST /v2/messages` |
| Выгрузка сообщений за период | да | `POST /v2/messages/messages_dump` + `GET /v2/messages/messages_dump/{export_id}` |
| Список контактов (с именем + chat_id + chat_type) | да | `GET /v2/contacts` |
| Создание/чтение/изменение группы | да | `POST /v2/groups`, `GET /v2/groups/{group_id}`, `PATCH /v2/groups/{group_id}` |
| **Список всех чатов канала** | **нет** | такого endpoint нет |
| Вебхуки: входящие, статусы, каналы, QR, группы | да | `POST /v2/webhooks` (событие `message.add` и др.) |

Важно: `chat_type` в Wazzup различает `whatsapp` (личный) и `whatsgroup` (групповой чат).

## 2. Главная находка: название чата уже приходит

Payload `message.add` по официальной документации Wazzup содержит:

```json
{
  "event": "message.add",
  "data": [{
    "message_id": "...",
    "chat_id": "221601332",
    "channel_id": "...",
    "direction": "inbound",
    "sender": {
      "chat_type": "telegram",
      "chat_id": "221601332",
      "name": "Test Testovich"
    },
    "recipient": {
      "chat_id": "221601332",
      "chat_type": "telegroup",
      "name": "Групповой чат",
      "...": "..."
    }
  }]
}
```

То есть по каждому входящему сообщению мы получаем:
- `recipient.name` — **название чата** (для группы — реальное название группы),
- `recipient.chat_type` — личный чат или группа,
- `sender.name` — имя отправителя,

А в нашем коде `app/api/wazzup/webhook/[token]/route.ts`:

- строки ~199–210: читаются `sender` и `contact`, но берётся **только телефон/chat_id**, поле `name` не читается;
- `insertPayload` не содержит ни `chat_name`, ни `chat_type`;
- строки ~274–289: фильтр `allowed_chat_ids` **уже работает** (если массив не пуст — сообщения из других чатов отбрасываются).

Вывод: механизм «обрабатываем только выбранные чаты» уже есть. Не хватает только
человеческого списка для выбора — и данные для него уже проходят через вебхук.

## 3. Вариант 0 — «список чатов по названию» без отказа от Wazzup

Объём работ:

1. Миграция: `chat_name text`, `chat_type text` в `wazzup_messages`
   (или отдельная таблица `whatsapp_chats` с upsert по `company_id + chat_id` — предпочтительнее,
   чтобы не дублировать название в каждом сообщении).
2. Вебхук: сохранять `recipient.name` / `sender.name` и `chat_type` при вставке.
3. Настройки WhatsApp: список чатов компании — название, тип (личный/группа), последнее сообщение,
   время; чекбокс «обрабатывать» → пишет `allowed_chat_ids` через уже существующий
   `app/api/wazzup/allowed-chats/route.ts`.
4. Бэкфилл: у уже накопленных `wazzup_messages` названий нет — либо подтянуть из `messages_dump`,
   либо просто начать собирать с момента релиза (старые чаты появятся при первом новом сообщении).

Оценка: 1–1.5 дня. Новых внешних зависимостей: 0. Рисков: 0.

## 4. Вариант A — официальный WhatsApp Cloud API (Meta)

Что даёт:
- легально, без риска бана;
- свой номер клиента, свой Meta app, вебхуки, медиа;
- сервисные сообщения в 24-часовом окне бесплатны; тарифы Meta менялись в октябре 2026 — считать по актуальному прайсу;
- режим Coexistence позволяет держать номер и в приложении WhatsApp, и в API.

Чего не даёт (критично для нашего сценария):
- **нет метода «список чатов»** — API вообще не отдаёт перечень диалогов;
- **групповые чаты** — поддержка появилась ограниченно и не как полноценный список групп
  (у BSP-провайдеров фигурирует как waitlist/beta). Для производства, где 90% трафика — рабочие группы,
  это стоп-фактор. **Требует отдельной проверки актуального статуса перед выбором этого пути.**
- нет истории сообщений до подключения;
- нужна верификация бизнеса в Meta (юридические документы компании клиента).

Итог: UX «клиент видит список своих чатов и отмечает нужные» на Cloud API **не реализуем**.

## 5. Вариант B — свой шлюз на Baileys (неофициально, как WhatsApp Web)

Состояние библиотеки (проверено 2026-11-08):
- репозиторий `WhiskeySockets/Baileys`: 11.5k звёзд, последний push — сегодня, не заархивирован;
- npm: `latest = 7.0.0-rc14`, стабильная ветка `legacy = 6.7.24`;
- вывод: проект живой и активно поддерживается, тезис «умирает» неверен.

Что даёт:
- QR-подключение как в WhatsApp Web, номер продолжает работать в телефоне;
- **полный список чатов с названиями**, включая группы и историю;
- медиа, голосовые, контакты;
- независимость от вендора и от ежемесячной платы за канал.

Риски:
- нарушает ToS WhatsApp → **возможен бан номера клиента**; для B2B, где номер — рабочий инструмент снабжения,
  это инцидент, а не мелочь. Митигация: только отдельный выделенный номер, не основной;
- не работает на Vercel: нужен постоянный процесс + персистентный диск для сессии
  (Railway / Fly.io / VPS, ~$5–20/мес на клиента или общий пул);
- обновления протокола WhatsApp: библиотека обновляется, но обновляться надо дисциплинированно;
- мультитенантность: сессии, шифрование ключей, изоляция — всё это надо строить и эксплуатировать самим;
- поддержка клиентов «у меня отвалился WhatsApp» становится нашей, а не Wazzup.

Оценка: шлюз 3–5 дней + постоянная эксплуатация. Плюс 1–2 дня на интеграцию в приложение.

## 6. Сравнение

| | Wazzup (сейчас) | Cloud API (Meta) | Свой шлюз (Baileys) |
|---|---|---|---|
| Список чатов с названиями | через вебхук (уже приходит) | нет | да, полный |
| Группы | да | ограниченно | да |
| QR-подключение клиентом | да (OAuth Label) | нет, верификация Meta | да |
| Риск бана номера | нет | нет | **есть** |
| Своя инфраструктура | не нужна | не нужна | нужен сервер + диск |
| Стоимость | платно за канал | по тарифу Meta | ~$5–20/мес + наше время |
| Кто держит поддержку | Wazzup | Meta/мы | **мы** |

## 7. Рекомендация

1. **Сейчас — Вариант 0.** Закрывает исходную боль («клиент не должен знать chat_id») за день,
   ничего не ломает, работает на текущем стеке. Это же решение останется валидным при любом
   будущем переходе — UI выбора чатов не зависит от того, кто стоит за вебхуком.
2. **Self-hosted шлюз — не сейчас и не вместо.** Если делать, то как отдельный сервис с нормальным
   процессом эксплуатации, и только когда Wazzup станет узким местом по деньгам или по возможностям
   (например, понадобится история чатов или произвольный разбор диалогов).
3. **Cloud API** для нашего сценария не подходит из-за отсутствия списка чатов и ограниченных групп.

## 8. Что осталось проверить (если пойдём дальше)

- Актуальный статус групповых чатов в Cloud API (waitlist / beta / GA) — на 2026-11-08 однозначного
  подтверждения получить не удалось, документация Meta по groups отдаёт 404.
- Точный формат `message.add`, который Wazzup присылает **именно нашему аккаунту**:
  в коде читается плоский `msg.contact`, в документации — вложенные `sender`/`recipient`.
  Нужно один раз посмотреть реальный payload в логах и сверить перед реализацией Варианта 0.
- Тарифы Meta после изменения расценок в октябре 2026.
